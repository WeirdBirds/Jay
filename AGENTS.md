## Lessons from user feedback

- Do not make claims about scene composition, counters, or config values until the relevant setup/meta files have been explicitly read; verify assumptions against source before reporting them as facts. Separate confirmed facts from speculation in all reports.
- For regressions, before editing, reproduce the issue, trace the failing data path and ownership contracts, and validate the root cause with targeted tests or probes; use targeted falsifiable probes instead of speculative fixes, and stop and reassess when evidence contradicts the hypothesis.
- Never run or propose launching the product/application itself without explicit user consent per session; treat routine internal implementation, test-harness, compile, and test details as pre-approved, resolve them autonomously, and never pause on them for approval; pause only for genuine product-scope decisions, destructive actions, or external blockers. Compile and locally validate each incremental test or implementation change before reporting progress or requesting decisions; do not claim a fix is complete until all required build tests and executable runtime smoke tests have been executed and their results verified; report exactly what passed, failed, and was not tested—if runtime launch lacks consent, report verification as incomplete; silently fix self-created defects, and report only verified results or genuine product decisions, destructive actions, or external blockers.
- Before acting, resolve any material scope, constraint, or term-meaning ambiguity; when a request has multiple plausible interpretations, explicitly confirm the intended scope before designing or coding; when a term has multiple plausible meanings, clarify which one is intended before proposing a design; when feedback is vague or heated, clarify which abstraction/ordering level is being designed and validate proposals against actual system constraints before presenting, like what is knowable under indirect draw and validate grouping assumptions against the actual indirect-draw path, keeping registry order separate from draw-pass order, instead of guessing or reversing a correct interpretation, and define any new terms on first use with clear status; if the workflow is already authorized and the requested change is clear from context, implement and verify it without presenting another plan, asking redundant follow-up questions, or requesting approval. Do not declare completion or request commit until all user-stated goals are addressed and verified; before reporting completion, re-check that every single item from the user's original request has been addressed, including removing all references to deprecated data and verifying no dead code remains. When a user asks for a review or cleanup pass, first complete and present a full audit, then execute the entire cleanup and implement all changes in one pass; only pause for approval on genuinely risky or ambiguous decisions, not routine deletions, except never skip approval for destructive file removals or git operations affecting uncommitted work without backup and a verified recovery path. Do not frame interim work with premature success summaries or demo-style explanations; wait until the entire cleanup is verified before editorializing. During diagnosis, carry through to fixes/actions by default without waiting for extra permission and only hold for approval if explicitly instructed; once approved, apply fixes, test, rerun, and commit when requested without seeking further approval unless a genuine ambiguity or destructive blocker arises. Once the user authorizes execution, autonomously debug and fix routine internal tooling, tests, test harnesses (including agent-authored test code), and implementation defects, then rerun tests and continue to completion without renewed approval; pause only for genuine product-scope decisions, destructive actions, or external blockers requiring user input. Clearly separate plans from shipped work in all status updates: label every item as planned, in-progress, or done, and never claim a review pass is complete until every discovered issue has been executed and verified. When a user says they want a 'proper review and cleanup pass', treat it as a directive to widen scope and find all related issues proactively—not just re-package the same narrow changes with more adjectives.
- Before claiming a rendering break, rule out camera placement and scene visibility with a pixel probe that would detect clear color versus rendered content, and state that assumption explicitly.
- When asked for a cleanup, always perform a holistic audit of the relevant codebase first and present a unified plan covering all discovered issues, not just the specific lines the user mentioned. Before performing cleanup or revisiting a touched area, search the codebase and re-read relevant prior context for any earlier user asks (e.g., already-requested removals), and include those in the cleanup scope rather than limiting to newly discovered items. Maintain an explicit session-long blacklist of every item the user has rejected or asked to remove, and check all new work against that blacklist before presenting changes. Re-verify this blacklist against every later edit to ensure previously rejected code or fields do not reappear. Before making changes in a cleanup pass, trace the full dependency graph of any removed feature—call sites, struct fields, shader mirrors, and infrastructure that only served that feature—and delete them comprehensively, not just the surface references. When a user requests a cleanup or review pass, scan all relevant files first, surface a complete list of issues, apply the full set of related changes in one uninterrupted pass, and report only when the entire consolidated edit set is actually complete. Treat any cleanup request as an invitation for a comprehensive dead-code audit across the touched subsystem; proactively identify and propose removal of all unused fields, functions, and debug scaffolding in one pass, not just the user's direct complaints. When a user requests a cleanup/removal pass, perform a thorough project-wide grep for all related symbols, call sites, and stale infrastructure before editing, and include every item found in the consolidated plan; if scope is already approved, execute it without renewed approval.
- Respect and remember user-imposed tooling constraints for the entire session; never propose workflows that violate an earlier explicit correction. Treat user tool/action constraints as absolute — stop the specific behavior immediately on first complaint and do not offer it again. Immediately stop and acknowledge when the user forbids a specific action; do not scope-creep or substitute similar unapproved actions without asking first. Never use shell commands like sed or perl for file modifications; always use the provided edit tool for any file content change and never propose shell-based text manipulation.
- When a user says to remove something (logs, fields, timing readouts), track that requirement explicitly and verify against it before claiming completion—never reintroduce removed items or leave redundant equivalents (e.g., re-adding ms/fps derived from a field the user already rejected). Before deleting or rewiring a metric, confirm what the user actually wants to remove versus keep, and preserve the original implementation's intent rather than swapping in a new mechanism unprompted. Before deleting functionality like timing/logging, check whether the user still needs the underlying capability and whether it can be sourced from existing infrastructure instead of being removed outright. Before removing logging/telemetry, distinguish between noise the user explicitly flagged and metrics that serve a purpose (e.g., FPS); if unsure, list each removal candidate with rationale for explicit approval rather than deleting broadly. Proactively restore useful features removed by a change using the correct existing source rather than asking the user or leaving the feature absent. Distinguish between removing a faulty implementation detail and removing a feature; preserve user-facing functionality like FPS display and re-derive it from a correct existing source (e.g., engine.timer.delta_time) rather than deleting it wholesale. When a user instructs removal of a specific item, verify the removal is complete across all references (field, assignments, call sites, logged columns) before moving on, and re-check that prior directives are fully honored. When removing a data source that fed a user-visible feature (e.g., FPS logging from a timing global), first identify and implement an alternative source so the feature remains intact before considering the removal complete.
- Treat explicit user constraints as hard gates: enumerate them before editing, verify every proposed change against them, and do not re-add or reintroduce prohibited items. If the user asks for a comprehensive review before changes, present the full review first before making any edits.
- When asked to perform a cleanup, do a genuinely thorough sweep and remove ALL dead code, unused fields, uncalled functions, orphaned infrastructure, and stale comments in one pass, including any now-dead call sites, fields, and infrastructure created by those removals. Verify with a final sweep across all touched files instead of relying on the initial scoped plan, and do not leave discoverable leftovers that require re-prompting. After executing any cleanup or refactor, perform a full verification sweep for dead code, unused fields, orphaned functions, and telemetry inconsistencies before reporting completion; report any remaining dead code unprompted in the same pass, and state explicitly what remains and why. Before reporting a cleanup/removal task as complete, run a systematic dead-code and orphan check across all modified subsystems (unused structs, functions, globals, shader branches, log columns, file stubs) and report every leftover finding in the same pass instead of forcing the user to ask 'what else is left'.
- Perform migrations and related changes end-to-end as one coordinated unit: update all dependents, fully remove legacy paths and derive all data from reflection rather than guessing hard-coded structs and update all call sites instead of leaving mixed old and new usage, build, run validation, and report incomplete blockers rather than presenting partial work as a fix. For authorized bug fixes, execute the full test-fix-test workflow without interim blocker reports: inspect and reuse the established testing and benchmarking conventions, infrastructure, and output formats rather than creating parallel harnesses, probes, benchmarks, APIs, or abstractions or weakening established coverage; add only the smallest necessary regression cases, demonstrate the failure, compile and validate test code before treating failures as implementation evidence, and silently correct test or implementation issues; exercise the same modules and public exports used in production, assert exact expected values rather than invariants alone, then validate from a clean state with the canonical full test suite, applicable benchmarks, integration checks, and a real consumer build, and create requested clean commits; report only after completion unless a true blocker requires user input. Make incremental buildable edits and verify build after each step, preserving working implementation until replacement is validated and preserving a buildable state throughout; never delete working code for guessed replacements or delete functional paths to patch with guesses; migrate incrementally; deliver a single, comprehensive result only when buildable throughout. For any cleanup or review request, treat the entire affected subsystem as the scope: enumerate every issue first, then execute fixes across all files in a single uninterrupted pass, and report done only after all findings are resolved—never satisfied by a single local edit. After any mass deletion or refactor, search for dangling references, unused allocations, dead branch code, and stale slot usage; verify build plus telemetry integrity before saying the work is done.
- Separate pure dead-code removals from changes that alter runtime behavior (memory usage, usage flags, allocation). Before any large refactor, restore, revert, checkout, broad rewrite, or historical-code edit, inspect repository status and file provenance, and back up current state with a recoverable patch, branch, or stash and verify diffs before any overwrite, delete, or git-restore of working files; preserve both old and new code until migration is verified, and verify exactly which working-tree changes will be affected; use non-destructive recovery steps first; inspect diffs before acting and verify file status afterward; never overwrite working files with historical versions or delete, overwrite, or git-remove files with uncommitted work without backup, explicit user confirmation, and verification with a restorable copy first; if state is uncertain stop edits and prioritize recovery. Verify behavior-affecting changes are within the approved scope; for bug fixes and recovery patches, change only the proven failing path with minimal, reversible edits; defer unrelated cleanup, API removal, behavior changes, and architectural refactoring until the broken path is restored and verified unless explicitly authorized; inspect the diff before reporting results; pause only when they require a genuine product decision.
- Do not declare a cleanup complete or say the code is all clean after addressing only the explicitly named items; perform a full project-wide sweep for dead code, unused fields, uncalled functions, and dead infrastructure in one pass before reporting completion.
- When removing code, remove only exactly what was requested or what is provably dead, except when a compile-time reflection workflow is required remove legacy runtime paths entirely and derive all fields strictly from shader reflection without hard-coding or preserving old APIs; preserve user-facing metrics and behavior unless explicitly told otherwise, and reuse existing data sources (like engine.timer.delta_time) instead of deleting features.
- During any cleanup, proactively identify and remove all temporary debug/probe/instrumentation code (probes, ground-truth comparisons, timestamps) that was added during investigation, not just the items explicitly listed by the user.
- After receiving approval to implement, autonomously decompose and complete the full end-to-end implementation in the same turn in one complete, uninterrupted pass leaving the build passing with real code changes, not placeholder updates; do not loop on confirmation or status messages or ask for approval again unless a genuine blocker is found; after approval for a multi-step task execute end-to-end without pausing for re-approval and do not return plans as progress.
- Before starting a cleanup task, scan the entire codebase for all related dead code, stale references, and unused infrastructure, then present one consolidated removal plan covering everything rather than making incremental changes.
- Before editing, inspect relevant code, plans, docs, and call paths; trace and document current call paths, ownership, data-flow invariants, established conventions, and explicit user constraints; state the verified architecture before proposing changes; before refactoring or changing subsystem architecture, trace the end-to-end data path including reflection-driven compile-time shader/material workflows, read all user-referenced code and experiments including referenced plans, subsystem documentation, relevant third-party library docs and code, and relevant implementation before drafting a plan, designing, or writing implementation code, infer fundamental system constraints and show how the plan respects them, mapping every stated requirement into the plan, and explicitly build the proposal on their proven patterns with each responsibility (codegen vs runtime) assigned and ordering and performance questions answered explicitly, then implement foundational contracts first in the prescribed architecture in plan-specified dependency order—when generated/reflected behavior is required, implement the source reflection pipeline first, implement dependencies before dependent code, and clarify compile-time vs runtime ownership first and derive generated types, constants, and layouts from the authoritative compile-time source such as shader reflection rather than hard-coding guessed fields, never hand-writing derived data, and preserve stated constraints and established mechanisms unless the user explicitly authorizes an architectural change; discover and reuse the canonical build/compile entry points and conventions before implementing and never introduce an alternative loading or compilation path; when migrating to a generative workflow remove deprecated handles/tables/runtime paths and derive all fields from reflection metadata rather than preserving old APIs or hand-writing stub structs; strictly follow the stated architectural workflow for all changes and derive all types from the source of truth; verify the complete existing contract across math code, APIs, consumers, renderer, shaders, and tests, prefer restoring the known working path over inventing replacement infrastructure, and explicitly separate confirmed requirements from assumptions. Trace cross-project dependencies before editing foundational conventions or consumers, keep changes tightly scoped to the requested task and only files proven necessary by that contract; do not alter ABI, defaults, docs, or unrelated files and review git status/diff for pollution before finishing; keep third-party and shared libraries generic and isolate product-specific mapping and domain-specific behavior in product-owned modules/product layers or general-purpose extensions and avoid unrelated refactors or domain-specific coupling, and explain any unavoidable cross-project scope expansion; preserve compatibility unless a migration is explicitly agreed; for agreed migrations, inventory all producers, consumers, and ABI/data-flow dependencies first, refactor incrementally within one continuous pass to a buildable, verified state, and remove legacy paths only after replacements are validated. Treat stated ABI/layout compatibility constraints as hard boundaries; enumerate and obtain explicit approval for any change that crosses them, with whole-project consumer analysis. When mirrored host/shader APIs or ABI layouts must change, update both sides atomically, clear/rebuild shader caches, and run full validation before reporting completion.
- Before claiming a task is complete, perform a final sweep for references to deleted functions/fields, unused parameters, stale comments, and broken feature toggles across all relevant files, not just the ones just edited. Before declaring a cleanup pass finished, independently audit for dead code, unused fields/functions, and stale references beyond the specific items first mentioned, and only report completion after a comprehensive sweep.
- When deciding what to keep vs. remove, clearly distinguish reusable library utilities from dead application code and document that boundary explicitly; if library utilities are kept, ensure all their callbacks and callers are either retained or fully removed.
- Before deleting diagnostics or timing code, confirm the desired end-state behavior (e.g., which metrics remain visible and from what source), then implement deletions and replacements in one coherent pass instead of incremental backtracking. Track prior user decisions and avoid reintroducing removed functionality; check existing engine utilities (e.g., engine.timer.delta_time) before adding new timing or diagnostic code.
- Whenever a shader-binding struct or buffer layout changes, explicitly clear or invalidate shader-derived caches (.jpkg, SPIR-V, etc.) as part of the same change, and add or suggest a build rule that detects content changes rather than path-only keys. Always force a shader recompile by clearing caches or bumping version keys before running, and mention this in the summary. After any change, verify runtime behavior and proactively explain expected counter values and gating states in release/run output so normal behavior is not mistaken for regression.
- When a user asks for 'cleanup' or 'a proper review pass', proactively sweep the entire related subsystem for dead code, stale fields, unused infrastructure, and latent bugs before touching anything, then present one complete plan covering all findings.
- When removing logs/timing machinery, distinguish the feature the user values (e.g., FPS telemetry) from the mechanism they called noise; preserve the feature, replace/clean the mechanism, and confirm scope before deleting global data that powers it.
- Treat CPU/GPU struct layouts and shader caches as one atomic unit: whenever a shared parameter struct or slang ABI field changes, update both sides and clear/recompile the shader cache in the same pass, and state explicitly that the GPU side was handled.
- When a user asks for a debug path, ensure the non-debug/release path removes the corresponding cost end-to-end (allocation, GPU writes, CPU reads), not just the visible readback, and proactively verify there is no hidden mirror traffic left. Verify both sides of debug/release gating: producer (GPU writes / allocations) and consumer (CPU reads) must both be compiled out, not just one side.
- For performance-sensitive libraries and hot-path math or transform code, establish necessity and scope and capture and preserve existing correctness, numerical-accuracy, and timing baselines with the project's standard benchmarks before editing, including representative and extreme supported-domain inputs checked against trusted references with explicit error bounds rather than self-consistency alone; retain changes only when they remain accurate and timing-non-regressive; preserve benchmark fidelity and revalidate both speed and accuracy after every relevant change; make minimal defect-specific changes, preserve existing fast paths, avoid speculative APIs or broader numerical behavior, require demonstrated callers, correctness tests, and clear value for every new API, branch, or behavior, and remove abstractions with no proven value, run the project's standard correctness tests plus focused and complete suites, audit the final diff for unnecessary complexity, and report verified comparative before/after benchmark results for every affected path before declaring completion.
- When rebuilding missing functionality, derive a concrete implementation contract from the project plan and existing design first, present it for approval, and do not edit until approved.
- Generalize helpers fully, remove dead/duplicated branches, and match established code style without prompting. Probe real API semantics first and use a single native mechanism instead of defensive duplicates; after splitting type kinds, audit for dead duplication and ensure each behavior has single ownership verified by probe.
- Prefer the minimal solution: skip no-ops, reuse existing identity, minimize resources, and avoid extra validation, hashing, or constraints unless proven necessary. Prefer simplest language-native identity (type identity, early-out on zero size) before building custom hashing, codegen, or abstraction layers; prefer the simplest idiomatic mechanism and handle edge cases with graceful no-ops rather than custom infrastructure, added validation, or asserts; do not add validation that blocks valid empty cases. Favor minimal-resource fixes, measure and present per-stage timings first, and surface resource vs complexity tradeoffs for approval before upsizing resources, justifying any increased usage with data.
- Execute the full requested scope to completion by default in one pass; do not withhold changes for approval unless destructive, never exclude work based on authorship or assumed ownership unless explicitly told to filter, and clearly report what was done.
- When a change spans shaders, materials, and pipelines, list all required steps together and explain why each step is needed for the effect; never give partial end-to-end instructions that omit required pipeline-state steps.
